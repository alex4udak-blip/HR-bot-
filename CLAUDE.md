# HR-bot — платформа найма (Enceladus)

## Локальный запуск
Конфиги лежат в `.claude/launch.json` (frontend + backend). Бэкенд читает
`backend/dev.env` (в git его нет — секреты).

```bash
cd frontend && node node_modules/vite/bin/vite.js --host        # UI :5173
cd backend && set -a && . ./dev.env && set +a && \
  ./.venv/bin/python -m uvicorn main:app --reload --port 8000   # API :8000
cd backend && ./.venv/bin/python -m pytest -q                   # тесты бэка
cd frontend && npx tsc --noEmit -p . && npx vitest run          # типы + тесты фронта
```

Локальные демо-аккаунты (пароль `Demo1234!`) создаёт `backend/seed_local.py`,
переключаться между ними удобнее через DEV-кнопку «Аккаунт» в левом нижнем углу
(только в dev-сборке): Super Admin, Настя и Мария (админы), Тестовый Рекрутёр и
Пётр (hr), Наблюдатель (readonly).

Грабли локального запуска:
- PostgreSQL (brew, `postgresql@17`) не стартует с «lock file postmaster.pid
  already exists» после перезагрузки Mac: PID в файле занят другим процессом.
  Проверь `ps -p <pid>` — если это не postgres, удали
  `/opt/homebrew/var/postgresql@17/postmaster.pid`, brew поднимет базу сам.
- Бэкенд через preview_start может не прочитать `dev.env` (macOS не пускает в
  Desktop) — тогда запускай его командой выше в фоновом терминале.
- Ключа Claude в `dev.env` нет: AI-разбор резюме локально не работает. Окно
  после разбора проверяют, подменив в браузере ответ на `/parser/resume/file`.
- В одной рабочей папке могут одновременно работать несколько вкладок Claude
  (например, дубли в соседней). Коммить только свои файлы по именам, никогда
  `git add -A`; соседняя вкладка может запушить и твои локальные коммиты.

**Эталон тестов** (эти падения были ДО правок, сверяйся с ними, а не с нулём):
- `vitest` — 0 падений (с 21.09.2026; до чистки было 241) — любое падение теперь НОВОЕ;
- `pytest tests/test_cross_org.py tests/test_entities*.py` — 26 падений;
- `pytest tests/test_vacanc*.py tests/test_kanban_privacy.py` — 25 падений.

## Деплой — Saturn (не Railway)
Панель: https://saturn.ac → проект Enceladus. Сервисы: **frontend**, **backend**,
**app**, postgresql-db, redis-cache. Всё на сервере saturn2.

- Рабочий адрес: **https://enceladus-7oylzk.saturn.ac** (бэк —
  `enceladus-ns9s2o.saturn.ac`, nginx фронта проксирует на него `/api`).
- `enceladus.site` — в петле редиректов, DNS смотрит не на тот сервер. Пока не
  починят, каноническим считается адрес saturn.ac (расширение переключено на
  него временно, см. `backend/chrome-extension/background.js`).
- **Деплой запускает человек** кнопкой Deploy в Saturn, автодеплой по пушу
  срабатывает не всегда. Бывало, что сборка «успешна», а сайт отдаёт старую:
  проверяй по факту, а не по статусу.

Проверка, что на проде реально новый код:
```bash
base=https://enceladus-7oylzk.saturn.ac
idx=$(curl -s "$base/?r=$RANDOM" | grep -o '/assets/index-[^"]*\.js' | head -1)
curl -sI "$base/?r=$RANDOM" | grep -i last-modified
curl -s "$base$idx" | grep -o 'assets/RecruiterFunnelsPage-[^"]*\.js' | head -1
# затем поискать в чанке строку из своего коммита
```

Бэкенд проще проверить GET-запросом к API из вкладки, где владелец залогинен
на проде (только чтение). Прод-базу смотрят в Saturn → postgresql-db → Query
Browser: он пропускает только SELECT, изменения данных — через код/миграцию.

## Роли
| Роль | Кто | Права |
|---|---|---|
| superadmin | платформа | всё |
| owner / admin | Настя, Мария | HR-сегмент целиком, аналитика, ПЭН, экспорт |
| hr | рекрутёры | кандидаты, воронки, вакансии, созвоны |
| member | сотрудники | без HR-раздела |
| is_readonly | наблюдатель | видит всё в HR, любые изменения блокируются в `get_current_user` |

`isHrAdmin` на фронте = superadmin, owner или admin.

## Модель работы HR
- **Кандидаты общие** для организации: смотреть и править может любой рекрутёр,
  неважно, кто добавил (`check_entity_access`, уровень edit). Удаление и передача
  — у автора и админов.
- **Воронка** = вакансия. Заявка (`VacancyApplication`) — связка кандидат↔вакансия,
  у неё свой этап. Заявку «берут в работу» лично (`extra_data.accepted_by`), в
  одной воронке может работать несколько рекрутёров (со-рекрутёры,
  `ApplicationCoRecruiter`). Кандидат может быть в нескольких воронках сразу —
  это норма.
- **«Забрать»** = ПЕРЕНОС кандидата к другому рекрутёру (для кандидатов
  уходящих рекрутёров): в этой воронке владелец заявки меняется на нового,
  прежний кандидата теряет; карточка («кто добавил») переходит тоже, если
  была за прежним. Если кандидата в воронке нет — он туда добавляется. Со
  28.08 по 21.09 кнопка работала аддитивно (добавляла со-рекрутёра); такие
  старые пары решено не трогать. Массовая передача всех воронок уходящего —
  отдельный механизм, `services/recruiter_transfer.py`.
- **Чей кандидат в воронке** = автор заявки (`created_by`), а если он пустой
  (старые данные, удалённый пользователь — FK `SET NULL`) — владелец вакансии.
  Одно правило и для метки «HR: …» (`services/hr_tags.py`), и для воронки со
  скоупом по рекрутёру (`recruiter_owns_application` в `vacancies/common.py`).
  Разъедутся — метка скажет «кандидат Марии», а в воронке Марии его не будет.
- **«Мои вакансии»** в сайдбаре = где ты лично принял. Выпадающий список там
  («Выбрать владельца вакансий») кладёт в адрес `?recruiter=<id>` — страница
  воронок показывает кандидатов этого человека. Работает для всех ролей.
- **«Только мои»** в воронке: в своей воронке включена при каждом входе
  (выключить можно только временно — другая воронка, уход, F5, новая вкладка
  снова включают; в браузере не хранится), в чужой выключена и временная, в
  воронке не в работе — неактивна.
- **«Все кандидаты»** — наоборот: всегда открываются со ВСЕМИ; «Только по моим
  вакансиям» в настройках списка временный и тоже не запоминается, «мой» =
  `recruiter_id` карточки (номер аккаунта, не имя). Сервер читает всех и
  считает бейджи точно, а карточек отдаёт до 2000 на этап без поиска и 500
  при поиске (туда подмешивается архив). «Показать ещё» только дорисовывает
  загруженное.
- **Бейдж и список не должны расходиться.** Счётчик считает сервер; если
  список дополнительно режется в браузере (фильтр, лимит), человек видит
  «Практика 9», а карточек 4 — так уже ломалось трижды. Любой фронтовый
  фильтр либо применяется и к счётчику, либо явно показывает, сколько скрыл.
- **«Выйти из вакансии»** (снять себя, у остальных остаётся) и **«Закрыть
  вакансию»** (закрыть у всех) — две разные кнопки, см. `getVacancyExitOptions`.
- **Вакансии-дубли** (две одинаковые воронки у одного человека — обычно после
  передачи от уходящего, у которого была своя копия) сливает админ:
  `POST /vacancies/{главная}/merge-from/{дубль}?dry_run=true` — сначала отчёт,
  `dry_run=false` — выполнить (`services/vacancy_merge.py`). Кандидаты дубля
  переезжают как есть; у кого заявка в обеих — остаётся этап главной, история и
  комментарии дубля приклеиваются к ней; дубль закрывается, не удаляется. Кнопки
  в интерфейсе нет. «Забрать» для этого НЕ годится: он меняет рекрутёра, а не
  вакансию.
- **Метки** (`entity_tags_catalog`) = только **сорсеры** (кто привёл кандидата,
  с 21.09.2026): всё, что вписали в метку, становится сорсером, выбора типа
  нет. Ставит любой рекрутёр. Метки вида «HR: Имя · Вакансия» — отдельно,
  считаются автоматически из заявок и не редактируются.
- **Теги у ФИО** («+ тег» рядом с именем) — СВОЙ справочник
  (`entity_name_tags_catalog` + `entity_name_tags`), с метками не связан.
  Разведение и одноразовая чистка меток-слов — `services/tags_split.py`
  (на старте; одноразовые шаги помечаются в `data_migration_marks`).
  Теги **Егор** и **Влад** — наставники практики: в «Все кандидаты» на
  вкладке «Практика» (ключ `probation`, только там) над списком строка
  «Практикуются у: Егор · N, Влад · N, без тега · N»; клик фильтрует список,
  повторный — снимает. Список имён — `PRACTICE_MENTOR_TAGS` в
  `candidateDetail/model.ts`; прочие теги только отображаются.
- **История этапов** (`StageTransition`): удаление ПОСЛЕДНЕЙ записи = отмена
  перевода — заявка возвращается на её `from_stage` (и общий статус кандидата
  пересчитывается), маркер `HISTORY_UNDO`. Старые записи выше по ленте —
  просто чистка лога, этап не трогаем (`HISTORY_DELETE`). Откат срабатывает
  только если `to_stage` записи совпадает с текущим этапом: этап уже подвинули
  руками — значит, запись его больше не описывает.
- **Окно «Сменить этап подбора»** (как в Huntflow, 23.09.2026): при открытии уже
  помечен СЛЕДУЮЩИЙ этап (`nextStageStatus` в `candidateDetail/model.ts`; отказ,
  резерв и архив сами не подставляются). Выбран этап, на котором кандидат уже
  стоит, — вместо поля комментария серая плашка «Кандидат сейчас находится на
  этом этапе подбора», «Сохранить» недоступно. После перевода карточка остаётся
  открытой, этап меняется на месте: ни тоста, ни перезагрузки, в воронке
  перемещённый кандидат закреплён в текущей вкладке, пока рекрутёр сам с неё не
  уйдёт (раньше он пропадал из списка и справа открывался следующий).

## Дубли кандидатов
Ведётся в отдельной вкладке Claude; актуальное состояние — в `git log` по
коммитам `(dubl)`. Уже есть единое ядро сравнения `services/duplicate_matcher.py`
(разные отчества — не точное совпадение), карусель похожих в окне сравнения,
текст резюме из файла без ИИ. Пополевое слияние сделали и откатили
(`1f38fd9a`): «Объединить» склеивает с одного клика. Красная плашка — только
когда совпало ≥2 признака, одно совпадение — жёлтая с процентом. Сравнение
НИКОГДА не ходит в Claude/OpenAI (дорого; сторожит `tests/test_dedup_no_ai.py`).
«Разные люди» (с 22.09.2026) — таблица `duplicate_pair_decisions`, одна строка
на пару, при слиянии переезжает на выжившую карточку
(`services/duplicate_decisions.py`); таблицу гарантирует `start.sh` ДО старта
сервера. Старый `extra_data.dismissed_duplicate_ids` перенесён один раз и ещё
читается как запасной.
Телефоны (с 22.09.2026) сравниваются в формате с кодом страны
(`services/phone_keys.py`, библиотека `phonenumberslite`): «+998 90…» = «90…»,
«+375 29…» = «80 29…». Местный номер без кода читается во всех странах СНГ
(`HOME_REGIONS`) — у него может быть несколько ключей; плюс старый ключ «10
цифр» для номеров, которых нет в таблицах. Разбор резюме больше не превращает
«8 029…» в «+7 029…». Отбор по заранее посчитанным ключам отложен: 1000 анкет
разбираются за ~50 мс, выигрыш не стоит риска устаревших ключей.
Правка ФИО/контактов/даты рождения/ссылки в карточке (PUT /entities)
сразу пересчитывает совпадения — у самой анкеты и у тех, чья плашка смотрела
на неё (`recheck_duplicates_after_edit`, маркер `DUP_RECHECK`); правка прочих
полей пересчёт не запускает. После «Сохранить» карточка берёт extra_data
целиком из ответа сервера. Все пять этапов переделки закрыты.
Служебные ящики сайтов вакансий (support@rabota.by, noreply@…, любой адрес на
hh.ru/rabota.by/superjob… — `is_service_email`) — не почта кандидата: в
сравнении не участвуют, расширение (с 1.8.9) и `/magic-button` их не сохраняют,
уже сохранённые убраны разово при старте (`service_email_cleanup.py`). Город в
процент совпадения и в причины НЕ входит (вписывают любой).
Ники-каналы порталов (hh_b2b, hh, telegram… — `JUNK_TELEGRAM_USERNAMES`) —
не Telegram кандидата: не сохраняются, убраны разово при старте, для показа
берётся первый НАСТОЯЩИЙ ник (`first_real_telegram` / `pickTelegram`), а не [0].
Контакты из ШАПКИ текста резюме (до первого раздела «Опыт работы»/«Желаемая
должность»…; строки с «руководитель», «контактное лицо» и т.п. пропускаются;
свободная форма — не берётся ничего) — `services/resume_contacts.py`, хранятся
в `extra_data.resume_contacts`. Совпадение по ним полноценное, подпись «(из
текста резюме)». Считаются при загрузке резюме, для старых — разово при старте.
Сканы и фото резюме распознаются Tesseract (rus+eng, в Dockerfile) в фоне
после загрузки (`ocr_and_store`, маркер `RESUME_OCR`): первые 4 страницы, в
отдельном потоке; без tesseract шаг просто пропускается. Старые сканы на
проде сами не распознаются — только новые загрузки.
Сверка всей базы («Сверить активных», «Найти дубликаты в архиве») группирует
анкеты по ПАРЕ «фамилия|имя», без отчества, и считает пары в отдельном потоке
(`scan_org_pairs`, маркер `DUP_SCAN`). Раньше группой было каждое слово ФИО:
7,5 млн пар, ~8 минут, сервер не отвечал никому (прод, 22.09.2026). Тяжёлые
разовые операции на проде ради замера не запускать — сначала воспроизводить
локально на данных того же объёма.

Окно сравнения решает пары по одной: кнопки действуют на анкету, открытую справа.

## Логи и диагностика
В бэкенде есть маркеры, по ним удобно искать в логах Saturn:
- `STAGE_CHANGE` — смена этапа: кто, заявка, кандидат, воронка, из→в;
- `STAGE_GUARD mismatch` — фронт просил сменить этап не тому кандидату (409);
- `HISTORY_DELETE` — удаление записи истории (без смены этапа);
- `HISTORY_UNDO` — удалена последняя запись → заявка вернулась на прежний этап;
- `TAKE_TRANSFER` — «Забрать»: заявка, кандидат, воронка, от кого → кому, кто нажал.
- `VACANCY_MERGE` — слияние вакансии-дубля: откуда → куда, сколько переехало и пересеклось.
- `DUP_DIFFERENT` — «Разные люди» по паре кандидатов; `DUP_DECISIONS merge` — перенос
  этих решений при объединении; `DUP_RECHECK` — пересчёт совпадений после правки карточки.

В консоли браузера смена этапа печатает `[stage] PUT application … → этап`.

## Правила работы в этом репозитории
- Работаем в рамках **HR-сегмента**: `/all-candidates`, `/statuses`, `/analytics`,
  `/my-funnels`, `/vacancies` и их бэкенд.
- Сначала проверяешь локально сам (тесты + браузер), потом отдаёшь на ручную
  проверку. Тестовые данные в локальной базе после проверки убираешь.
- В панели Saturn — только чтение. Любое изменение переменных, деплой,
  перезапуск — после явного «да» от владельца.
- Никогда не запускать `docker system prune --volumes` / `docker volume prune`
  на сервере: снесёт том PostgreSQL.
