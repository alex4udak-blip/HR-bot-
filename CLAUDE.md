# HR-bot — платформа найма (Enceladus)

## Локальный запуск
Конфиги лежат в `.claude/launch.json` (frontend + backend). Бэкенд читает
`backend/dev.env` (в git его нет — секреты).

```bash
cd frontend && node node_modules/vite/bin/vite.js --host        # UI :5173
cd backend && set -a && . ./dev.env && set +a && \
  ./.venv/bin/python -m uvicorn main:app --reload --port 8000   # API :8000
cd backend && ./.venv/bin/python -m pytest -q                   # тесты бэка
cd frontend && npx tsc --noEmit -p . && npx vitest run          # типы + тесты фронта
```

Локальные демо-аккаунты (пароль `Demo1234!`) создаёт `backend/seed_local.py`,
переключаться между ними удобнее через DEV-кнопку «Аккаунт» в левом нижнем углу
(только в dev-сборке): Super Admin, Настя и Мария (админы), Тестовый Рекрутёр и
Пётр (hr), Наблюдатель (readonly).

Грабли локального запуска:
- PostgreSQL (brew, `postgresql@17`) не стартует с «lock file postmaster.pid
  already exists» после перезагрузки Mac: PID в файле занят другим процессом.
  Проверь `ps -p <pid>` — если это не postgres, удали
  `/opt/homebrew/var/postgresql@17/postmaster.pid`, brew поднимет базу сам.
- Бэкенд через preview_start может не прочитать `dev.env` (macOS не пускает в
  Desktop) — тогда запускай его командой выше в фоновом терминале.
- Ключа Claude в `dev.env` нет: AI-разбор резюме локально не работает. Окно
  после разбора проверяют, подменив в браузере ответ на `/parser/resume/file`.
- В одной рабочей папке могут одновременно работать несколько вкладок Claude
  (например, дубли в соседней). Коммить только свои файлы по именам, никогда
  `git add -A`; соседняя вкладка может запушить и твои локальные коммиты.

**Эталон тестов** (эти падения были ДО правок, сверяйся с ними, а не с нулём):
- `vitest` — 0 падений (с 21.09.2026; до чистки было 241) — любое падение теперь НОВОЕ;
- `pytest tests/test_cross_org.py tests/test_entities*.py` — 26 падений;
- `pytest tests/test_vacanc*.py tests/test_kanban_privacy.py` — 25 падений.

## Деплой — Saturn (не Railway)
Панель: https://saturn.ac → проект Enceladus. Сервисы: **frontend**, **backend**,
**app**, postgresql-db, redis-cache. Всё на сервере saturn2.

- Рабочий адрес: **https://enceladus.site** (бэк — `enceladus-ns9s2o.saturn.ac`,
  nginx фронта проксирует на него `/api`). С 10.09 по 24.09.2026 каноном был
  временно `enceladus-7oylzk.saturn.ac`: `enceladus.site` уходил в петлю
  редиректов из-за DNS. Починили — вернули.
- Старый адрес `enceladus-7oylzk.saturn.ac` ведёт в ТОТ ЖЕ контейнер фронта
  (два имени у одного nginx). Его страницы отдают 301 на `enceladus.site`
  (`map $host $is_legacy_host` в `frontend/nginx.conf`), а `/api` и `/miniapp`
  редиректа НЕ имеют намеренно: расширения прошлых версий ходят на старый
  `/api`, а при кросс-доменном редиректе браузер выбрасывает `Authorization` и
  превращает POST в GET — кнопка ломалась бы молча. Адрес мини-аппа прописан в
  BotFather, его переключают вместе с ним.
- **Деплой запускает человек** кнопкой Deploy в Saturn, автодеплой по пушу
  срабатывает не всегда. Бывало, что сборка «успешна», а сайт отдаёт старую:
  проверяй по факту, а не по статусу.

Проверка, что на проде реально новый код:
```bash
base=https://enceladus.site
idx=$(curl -s "$base/?r=$RANDOM" | grep -o '/assets/index-[^"]*\.js' | head -1)
curl -sI "$base/?r=$RANDOM" | grep -i last-modified
curl -s "$base$idx" | grep -o 'assets/RecruiterFunnelsPage-[^"]*\.js' | head -1
# затем поискать в чанке строку из своего коммита
```
Бэкенд проще проверить GET-запросом к API из вкладки, где владелец залогинен
на проде (только чтение). Прод-базу смотрят в Saturn → postgresql-db → Query
Browser: он пропускает только SELECT, изменения данных — через код/миграцию.

## Роли
| Роль | Кто | Права |
|---|---|---|
| superadmin | платформа | всё |
| owner / admin | Настя, Мария | HR-сегмент целиком, аналитика, ПЭН, экспорт |
| hr | рекрутёры | кандидаты, воронки, вакансии, созвоны |
| member | сотрудники | без HR-раздела |
| is_readonly | наблюдатель | видит всё в HR, любые изменения блокируются в `get_current_user` |

`isHrAdmin` на фронте = superadmin, owner или admin.

### «Наблюдатель» (`OrgMember.is_readonly`) — смотреть можно всё, трогать нельзя
Ментор (Егор, Влад — 01.10.2026: «Ты должен видеть кандидатов, но просто не
исправлять»). Флаг обычно висит поверх прав админа, поэтому «само» ничего не
отключается — каждое место закрывают явно:
- **Сервер** — одна точка `get_current_user` → `observer_check_needed(method, path)`
  в `services/auth.py`: любой не-GET вне белого списка даёт 403. Белый список
  (`OBSERVER_WRITABLE_PREFIXES`) — это СВОЙ домен наблюдателя: auth, Практика
  (чаты/созвоны/практиканты/критерии), проекты, отпуска, блокеры, свои
  уведомления; практик-лид с этим флагом работает там как обычно.
- **Клиент** — тот же список в `services/api/client.ts`
  (`OBSERVER_WRITABLE_PREFIXES`, `isObserverBlocked`, включается из `authStore`).
  Изменяющий запрос не уходит вовсе, человек видит одно сообщение. Раньше 403
  гасили молча, и выглядело это как «кнопка сломалась»: комментарий «отправлен»,
  этап «сменился» и вернулся после F5. **Правите список — правьте оба.**
- **Интерфейс** — кнопок записи у наблюдателя нет: «+» в HR-сайдбаре, создание и
  правка вакансий/заявок, «Взять в работу»/«Отказаться», массовая плашка,
  «Поделиться» (она СОЗДАЁТ публичную ссылку), метки, реакции, чипы «Файл»/
  «Анкета» (окно СОЗДАНИЯ анкеты), меню записи в ленте. Форма вакансии
  открывается в режиме просмотра (`isReadOnlyRequest`).
- **Что он при этом видит — ВСЁ.** Лента карточки (переходы + комментарии),
  фильтр «Действия», файлы со скачиванием, ответы кандидата во вкладке «Анкета»,
  чужие воронки, аналитика.
- Грабли, из-за которых чинили: в `CandidateVacancyCard` один флаг `readonly`
  означал и «нельзя нажимать», и «это снапшот влитого дубля, истории у него
  нет» — наблюдателю карточка открывалась с ПУСТОЙ лентой. Теперь снапшот —
  отдельный проп `snapshot`, а `readonly` только убирает кнопки.
- Не закрыто: страница «Статусы» (её в тот момент переписывала соседняя вкладка)
  и страницы настроек HR — там кнопки ещё выглядят активными, но запись режется
  клиентским стражем с сообщением. Довести до вида «кнопок нет» — отдельной
  задачей.

### Скоуп по воронкам: «вижу только свою воронку»
Продолжение истории (01.10.2026, Мария): «давать доступ полностью ко всей базе не
нужно, мы им нанимаем в трафик — значит доступ только к трафику». До этого
кандидаты были ОБЩИМИ для организации, сужения не было вовсе.

- Хранится в `org_members.scope_vacancy_ids` (JSON, список id вакансий).
  **Пусто/NULL — ограничения НЕТ** (поведение всех существующих людей не
  изменилось); непустой список — видны только кандидаты с заявкой в этих
  воронках и сами эти воронки. Суперадмина скоуп не касается.
- Ставится галочками: Настройки → Пользователи → карточка человека, блок «Какие
  воронки видит» (виден, когда роль «Наблюдатель»). Эндпоинты:
  `PATCH /users/{id}` (суперадмин) и `PATCH /organizations/current/members/{id}/role`
  (админ орга); чужие вакансии из списка отсекаются по org_id.
- Вся логика — `services/vacancy_scope.py`. Проверки стоят в ДВУХ горлышках, а не
  по эндпоинтам: `check_entity_access` (любой доступ к карточке) и фильтр в
  запросах списков (`_base_candidate_query`, `/entities`, список вакансий).
  Плюс `ensure_vacancy_visible` на ручках вакансии и `ensure_entity_visible` на
  «мелких» ручках кандидата (метки, анкеты, история писем, рекомендации,
  staff-status, сквозная история этапов) — они достают данные по entity_id мимо
  check_entity_access, и без этой строчки чужой кандидат утекал по кусочкам
  (нашлось при аудите: 7 ручек отдавали 200).
- Чужая воронка/кандидат отвечают **404, а не 403**: сам факт существования —
  тоже информация, а id перебираются.
- Кандидат в двух воронках, одна из которых разрешена: сам он виден, но блок
  чужой воронки в карточке скрыт (`/entities/{id}/activity` фильтрует заявки).
- Баннер наблюдателя при непустом скоупе меняет текст на «доступ только к вашим
  воронкам» — «вы видите всё» было бы неправдой.
- НЕ ограничены намеренно (решение владельца 01.10.2026): «Статусы» (дашборд
  практики/отделов — Мария назвала его открытой информацией), «Аналитика»,
  «Заявки», «Анкеты». Если потребуется — скоупить там же, через
  `get_scope_vacancy_ids`.
- Проверялось на локальной копии прод-воронки «Трафик» (635 заявок, то же
  распределение по этапам и рекрутёрам; имена синтетические — персональные
  данные с прода не выгружались). Скрипт: `seed_scope_test.py` в scratchpad
  сессии, с ключом `--clean`.

## Модель работы HR
- **Кандидаты общие** для организации: смотреть и править может любой рекрутёр,
  неважно, кто добавил (`check_entity_access`, уровень edit). Удаление и передача
  — у автора и админов.
- **Воронка** = вакансия. Заявка (`VacancyApplication`) — связка кандидат↔вакансия,
  у неё свой этап. Заявку «берут в работу» лично (`extra_data.accepted_by`), в
  одной воронке может работать несколько рекрутёров (со-рекрутёры,
  `ApplicationCoRecruiter`). Кандидат может быть в нескольких воронках сразу —
  это норма.
- **«Забрать»** = ПЕРЕНОС кандидата к другому рекрутёру (для кандидатов
  уходящих рекрутёров): в этой воронке владелец заявки меняется на нового,
  прежний кандидата теряет; карточка («кто добавил») переходит тоже, если
  была за прежним. Если кандидата в воронке нет — он туда добавляется. Со
  28.08 по 21.09 кнопка работала аддитивно (добавляла со-рекрутёра); такие
  старые пары решено не трогать. Массовая передача всех воронок уходящего —
  отдельный механизм, `services/recruiter_transfer.py`.
- **Чей кандидат в воронке** = автор заявки (`created_by`), а если он пустой
  (старые данные, удалённый пользователь — FK `SET NULL`) — владелец вакансии.
  Одно правило и для метки «HR: …» (`services/hr_tags.py`), и для воронки со
  скоупом по рекрутёру (`recruiter_owns_application` в `vacancies/common.py`).
  Разъедутся — метка скажет «кандидат Марии», а в воронке Марии его не будет.
- **«Мои вакансии»** в сайдбаре = где ты лично принял. Выпадающий список там
  («Выбрать владельца вакансий») кладёт в адрес `?recruiter=<id>` — страница
  воронок показывает кандидатов этого человека. Работает для всех ролей.
- **«Только мои»** в воронке: в своей воронке включена при каждом входе
  (выключить можно только временно — другая воронка, уход, F5, новая вкладка
  снова включают; в браузере не хранится), в чужой выключена и временная, в
  воронке не в работе — неактивна.
- **«Все кандидаты»** — наоборот: всегда открываются со ВСЕМИ; «Только по моим
  вакансиям» в настройках списка временный и тоже не запоминается, «мой» =
  `recruiter_id` карточки (номер аккаунта, не имя). Сервер читает всех и
  считает бейджи точно, а карточек отдаёт до 2000 на этап без поиска и 500
  при поиске (туда подмешивается архив). «Показать ещё» только дорисовывает
  загруженное. В строке списка у кандидата чип этапа НА КАЖДУЮ воронку
  («Выполняет ТЗ · Трафик»), а если воронок нет — его общий статус без названия
  воронки (`buildListRowStages`; запрос владельца 23.09.2026 — «пусть этап
  показывается у всех»).
- **Поиск кандидата** (одно окно, `services/search_index.apply_text_search` —
  общий для `/candidates/search`, `/kanban` и `/ids`, чтобы «Выбрать всех»
  отбирало ровно тех, кого показал список). Обычный запрос ищет по имени
  (pg_trgm: транслит, любой порядок слов, опечатки), контактам, должности,
  компании и тексту комментариев; весь `extra_data`-блоб НЕ ищется (шум).
  Запрос с «**@**» — это запрос НИКА: сам «@» срезается, но поиск переключается
  в строгий режим «telegram + комментарии + контакты из шапки резюме», без
  нечёткого имени (иначе ник тащил чужие карточки). Если по нику НИЧЕГО нет —
  откатываемся к обычному поиску и подписываем список: «По нику … ничего не
  нашли — показываем совпадения по имени и контактам» (`nick_fallback` в ответе
  `/kanban`). Без отката получался тупик: «@shaffer_art» — пусто, а тот же текст
  без «@» находил человека по ФИО, потому что в карточке ник сохранён обрезанным
  (`shaffer_a`, 01.10.2026).
- **Добавили кандидата — открывается ЕГО карточка** (просьба Эльвиры
  02.10.2026). Окно разбора резюме само создаёт человека и отдаёт наверх его id
  (`onCreated`; при прикреплении резюме к существующему — `onAttachedToEntity`),
  страница открывает эту карточку, сбрасывая поиск и вкладку на «Все» — иначе
  новый «Новый» не попал бы в текущий фильтр. Раньше справа оставался тот, кто
  был открыт ДО добавления: «можно на бегу не тому статусы поменять».
- **Поиск в «Все кандидаты» не должен тихо висеть.** Раньше он занимал место
  полосы этапов (теперь — отдельная строка ПОД ними, 02.10.2026), поэтому
  набранное легко забыть, а список молча продолжает резаться —
  «тыкаем вкладку, а она не отрабатывает» (Эльвира, 02.10.2026). Поэтому строка
  поиска живёт ТОЛЬКО пока ищут: крестик, Escape, лупа, клик по вкладке этапа и
  «Все кандидаты» в меню — всё это и очищает запрос, и убирает саму строку
  (пустому полю под этапами места не занимать, владелец 02.10.2026); пункт меню
  ещё и возвращает на вкладку «Все». Метка перехода из меню — `state={{ resetSearch: true }}` у
  NavLink в `Layout`, страница ловит её по смене `location.key`: наши
  собственные правки адреса (`?entity=…`) такой метки не несут и поиск не сбивают.
- **Бейдж и список не должны расходиться.** Счётчик считает сервер; если
  список дополнительно режется в браузере (фильтр, лимит), человек видит
  «Практика 9», а карточек 4 — так уже ломалось трижды. Любой фронтовый
  фильтр либо применяется и к счётчику, либо явно показывает, сколько скрыл.
- **«Выйти из вакансии»** (снять себя, у остальных остаётся) и **«Закрыть
  вакансию»** (закрыть у всех) — две разные кнопки, см. `getVacancyExitOptions`.
- **Вакансии-дубли** (две одинаковые воронки у одного человека — обычно после
  передачи от уходящего, у которого была своя копия) сливает админ:
  `POST /vacancies/{главная}/merge-from/{дубль}?dry_run=true` — сначала отчёт,
  `dry_run=false` — выполнить (`services/vacancy_merge.py`). Кандидаты дубля
  переезжают как есть; у кого заявка в обеих — остаётся этап главной, история и
  комментарии дубля приклеиваются к ней; дубль закрывается, не удаляется. Кнопки
  в интерфейсе нет. «Забрать» для этого НЕ годится: он меняет рекрутёра, а не
  вакансию.
- **Метки** (`entity_tags_catalog`) = только **сорсеры** (кто привёл кандидата,
  с 21.09.2026): всё, что вписали в метку, становится сорсером, выбора типа
  нет. Ставит любой рекрутёр. Метки вида «HR: Имя · Вакансия» — отдельно,
  считаются автоматически из заявок и не редактируются.
- **Теги у ФИО** («+ тег» рядом с именем) — СВОЙ справочник
  (`entity_name_tags_catalog` + `entity_name_tags`), с метками не связан.
  Разведение и одноразовая чистка меток-слов — `services/tags_split.py`
  (на старте; одноразовые шаги помечаются в `data_migration_marks`).
  Теги **Егор** и **Влад** — наставники практики: в «Все кандидаты» на
  вкладке «Практика» (ключ `probation`, только там) над списком строка
  «Практикуются у: Егор · N, Влад · N, без тега · N»; клик фильтрует список,
  повторный — снимает. Список имён — `PRACTICE_MENTOR_TAGS` в
  `candidateDetail/model.ts`; прочие теги только отображаются.
- **Лента карточки** (24.09.2026, разбор с Марией). Одна запись = одно событие:
  строка «СТАТУС — комментарий», без стрелок «из → в» и без приставки «Этап:».
  Комментарий из окна смены этапа уходит ВМЕСТЕ с переводом (в
  `StageTransition.comment`), а не отдельной заметкой — раньше одно действие
  давало две строки, и было непонятно, к какому этапу относится текст. Прежний
  этап показывается подсказкой при наведении на статус. Кнопки «+коммент»
  больше нет: у строки только «Скопировать» и меню по шеврону — Редактировать /
  Закрепить (Открепить) / Удалить. Правка пишет `edited_at`/`edited_by`: в
  строке остаётся автор и время НАПИСАНИЯ, пометка «Изменено» и подсказка «кто
  и когда правил» — отдельно (время местное у смотрящего, пояс подписан).
  Закреп — ОДИН на воронку (`vacancy_applications.pinned_entry_key`), общий для
  всех, показывается первым и со своего места по дате уходит; у кандидата в
  двух воронках закрепов два, каждый в своём блоке. У кандидата ВНЕ воронок
  заявки нет, поэтому закреп лежит на карточке (`entities.extra_data
  .pinned_entry_key`, эндпоинт `PUT /entities/{id}/pin`). Длинный комментарий
  сворачивается с заметной кнопкой «Показать ещё».
- **Кандидат ВНЕ воронок двигается по этапам так же.** Заявки у него нет, писать
  `StageTransition` некуда, поэтому запись о переводе живёт комментарием
  (`extra_data.notes`, поля `stage` + `from_status`). Такая запись создаётся при
  КАЖДОМ переводе, даже без комментария (тогда у неё пустой текст и в ленте
  видна одна строка со статусом) — иначе этап менялся молча и следа не
  оставалось. Обычный комментарий без текста по-прежнему не сохраняется. Удаление такой записи
  возвращает кандидата на прежний статус — как корзина у записи истории в
  воронке (маркер `NOTE_STAGE_UNDO`; требование владельца 28.09.2026: «неважно,
  воронка это или нет»). Откат срабатывает, только если запись описывает
  ТЕКУЩИЙ статус.
- **История этапов** (`StageTransition`): удаление ПОСЛЕДНЕЙ записи = отмена
  перевода — заявка возвращается на её `from_stage` (и общий статус кандидата
  пересчитывается), маркер `HISTORY_UNDO`. Старые записи выше по ленте —
  просто чистка лога, этап не трогаем (`HISTORY_DELETE`). Откат срабатывает
  только если `to_stage` записи совпадает с текущим этапом: этап уже подвинули
  руками — значит, запись его больше не описывает.
- **Окно «Сменить этап подбора»** (как в Huntflow, 23.09.2026): при открытии уже
  помечен СЛЕДУЮЩИЙ этап (`nextStageStatus` в `candidateDetail/model.ts`; отказ,
  резерв и архив сами не подставляются). Выбран этап, на котором кандидат уже
  стоит, — вместо поля комментария серая плашка «Кандидат сейчас находится на
  этом этапе подбора», «Сохранить» недоступно. После перевода карточка остаётся
  открытой, этап меняется на месте: ни тоста, ни перезагрузки, в воронке
  перемещённый кандидат закреплён в текущей вкладке, пока рекрутёр сам с неё не
  уйдёт (раньше он пропадал из списка и справа открывался следующий).
- **Окно смены этапа не предлагает того, чего заявке поставить нельзя.** Пикер
  на «Все кандидаты» строится из колонок доски через `buildStagePickerOptions`,
  и служебная «Вне воронки» (`BOARD_OTHER_STATUS`) из него ВЫРЕЗАНА: у заявки
  такого этапа нет, сохранение не слало на сервер ничего, а карточку на доске
  двигало — «перевёл, а он на месте» (Гром Виктор, 24.09.2026). Если статус без
  пары среди этапов заявки всё же попадёт в окно, `cardChangeStage` показывает
  ошибку и НЕ двигает карточку: молчаливых переводов быть не должно.
- **Кандидат в нескольких воронках.** У каждой воронки свой этап и своя карточка
  в стеке; общий статус (колонка «Все кандидаты») сервер считает по «актуальной»
  заявке — самой свежей ЖИВОЙ, отказ/резерв учитываются, только когда живых не
  осталось. Поэтому отказ в ОДНОЙ воронке не уводит кандидата в колонку «Отказ»,
  пока он работается в другой. Фронт ставит карточку в колонку по полю
  `entity_status`, которое возвращают `PUT /vacancies/applications/{id}` и
  удаление записи истории, — не по выбранному этапу: иначе до F5 список
  расходился с сервером.

## Доска «Статусы»: песочницы и назначения (30.09.2026)
Строка доски — **назначение** (`staff_board_placements`): человек в конкретном
отделе. У одного человека их может быть несколько, карточка кандидата при этом
ОДНА (`entity_id` у таких строк совпадает, дубля в базе нет).

- **Песочница — родительский отдел** (`staff_board_departments.kind='sandbox'`:
  SANDBOX, SANDBOX MOBILE, SANDBOX R&D), команда (Facebook, Google, SEO…) —
  дочерний, у неё `parent_id` песочницы. Как в ООП: песочница — родитель,
  команда — потомок, человек — объект.
- **Перевод с практики в отдел — не переезд, а ещё одна ссылка**: в песочнице
  человек ОСТАЁТСЯ. В строке песочницы выбор отдела ДОБАВЛЯЕТ назначение
  (`POST /staff-board/placements`), в строке команды — переносит
  (`replace_placement_id`), «×» убирает из отдела; песочницу снимает только
  админ.
- **Даты и вехи — у назначения** (`BoardPlacement.extra`, те же ключи, что были
  в карточке): в песочнице живут даты практики, в команде — выход в отдел и
  вехи от него. Поэтому PATCH строки всегда шлёт `placement_id`.
- **Статус — у человека**, один на все строки: уволили в команде — уволен и в
  песочнице, строки остаются видны в группе «Уволен / Уволился».
- **«Все» показывает человека один раз** (строка команды главнее песочницы),
  бейдж «Все» считает людей, а не строки; у отделов — строки.
- **Видимость отдела**: `visibility` = all / custom + `visible_to`. Админы
  (superadmin, owner, admin) видят все отделы, рекрутёр — только «виден всем» и
  те, где его назвали. Невидимый отдел не прячет человека: он показывается
  строкой «без отдела».
- **Песочница у вакансии** — `Vacancy.extra_data["board_sandbox_id"]`, поле
  «Песочница на практике» в форме вакансии. С выходом на практику человек
  встаёт в неё сам (`ensure_sandbox_placement`, маркер `BOARD_PLACEMENT auto`);
  не выбрана — ждёт в «Без отдела», угадывать песочницу нельзя.
- **Разовый перенос старых данных** — `services/board_placements.py`
  (`extra_data.board_department_id` → назначения, отделы с именем SANDBOX*
  получают роль песочницы). Практикантов без отдела ни в какую песочницу не
  раскладываем — это делает HR.
- Подпись «Сандбокс» в колонках должности и отдела у практикантов убрана:
  песочница теперь настоящий отдел, а должность вписывает HR.

## Новые колонки в базе (правило после аварии 28.09.2026)
Миграции Alembic в репозитории поломаны, колонки заводятся «страховками». Класть
новую колонку в ХВОСТ общего ensure-блока `start.sh` НЕЛЬЗЯ: этот блок — один
python-скрипт на 800 строк, первая же ошибка внутри обрывает его целиком, а
снаружи стоит `|| echo`, поэтому провал выглядит в логе как успех. Так 28.09
уехал код с `vacancy_applications.pinned_entry_key` без самой колонки: SQLAlchemy
перечисляет ВСЕ поля модели в каждом SELECT, поэтому падали любые запросы к
заявкам — у рекрутёров не открывалась карточка и не двигались кандидаты.

Как правильно:
1. колонку — в `init_database()` (`api/db/init.py`, шаг 3.0), каждую своей
   `run_migration`: падение соседней не мешает;
2. проверять локально ТЕМ ЖЕ путём, каким она поедет на прод: снести колонку
   (`ALTER TABLE … DROP COLUMN`) и поднять бэкенд заново, а не создавать её
   руками через psql;
3. после деплоя дёрнуть то, что её читает (карточка кандидата, воронка), а не
   только проверить, что фронт новый.

При старте приложение сверяет модели с базой и пишет `SCHEMA_DRIFT` — «в базе
нет колонок: …». Если такая строка есть в логе деплоя, раздел уже сломан: надо
заводить колонку, а не ждать жалоб.

## Логи и диагностика
В бэкенде есть маркеры, по ним удобно искать в логах Saturn:
- `STAGE_CHANGE` — смена этапа: кто, заявка, кандидат, воронка, из→в;
- `STAGE_GUARD mismatch` — фронт просил сменить этап не тому кандидату (409);
- `HISTORY_DELETE` — удаление записи истории (без смены этапа);
- `HISTORY_UNDO` — удалена последняя запись → заявка вернулась на прежний этап;
- `NOTE_STAGE_UNDO` — удалена запись о переводе у кандидата вне воронок → статус вернулся;
- `HISTORY_EDIT` — поправили комментарий к переводу; `ENTRY_PIN` — закрепили/открепили запись ленты;
- `TAKE_TRANSFER` — «Забрать»: заявка, кандидат, воронка, от кого → кому, кто нажал.
- `VACANCY_MERGE` — слияние вакансии-дубля: откуда → куда, сколько переехало и пересеклось.
- `SCHEMA_DRIFT` — при старте: колонки моделей, которых нет в базе (пусто = всё сошлось).
- `DUP_DIFFERENT` — «Разные люди» по паре кандидатов; `DUP_DECISIONS merge` — перенос
  этих решений при объединении; `DUP_RECHECK` — пересчёт совпадений после правки карточки.

В консоли браузера смена этапа печатает `[stage] PUT application … → этап`.

## Правила работы в этом репозитории
- Работаем в рамках **HR-сегмента**: `/all-candidates`, `/statuses`, `/analytics`,
  `/my-funnels`, `/vacancies` и их бэкенд.
- Сначала проверяешь локально сам (тесты + браузер), потом отдаёшь на ручную
  проверку. Тестовые данные в локальной базе после проверки убираешь.
- В панели Saturn — только чтение. Любое изменение переменных, деплой,
  перезапуск — после явного «да» от владельца.
- Никогда не запускать `docker system prune --volumes` / `docker volume prune`
  на сервере: снесёт том PostgreSQL.
